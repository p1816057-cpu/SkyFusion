# 通用开发模板 · 需求处理两种模式

> 两个模板都**不绑定任何技术栈**（不限语言、框架、平台、行业），可以用在任何软件项目上。
> 模板正文是给 AI 编码助手看的"行为契约"，复制走就能用。

---

## 一句话区分

| | **模板 1 · 自主决策版（懒人版）** | **模板 2 · 需求确认版（精细版）** |
| --- | --- | --- |
| 一句话 | 你少说话，AI 多做主；**换技术栈、动架构、花钱、破坏性操作必须问你** | 开工前必须把需求确认到 **95% 以上**，任何不清楚都要问 |
| 谁做决定 | 细节 AI 定，重大变更你定 | 全部你定，AI 只负责问清楚 + 执行 |
| 你要投入 | 低：一句话需求 + 回答少量红线问题 | 高：回答多轮问题 + 确认需求书 |
| AI 什么时候问你 | 只命中红线时 | 只要它不确定 |
| 出错风险 | AI 可能选了你不喜欢的实现方式（但核心需求受保护，大变更会问） | 几乎没有"理解偏差"风险，但前期耗时更长 |
| 典型产出 | 可运行成品 + 决策记录表 | 需求规格确认书 + 可运行成品 |
| 适合 | 个人小工具、原型验证、你自己也没想清楚的场景、信任 AI 判断 | 商业交付、团队协作、需求复杂、出错代价高、需要验收 |

---

## 怎么选

按顺序问自己：

1. **做错了重来的代价高吗？** 高 → 模板 2
2. **这东西要交给别人 / 客户，需要验收吗？** 要 → 模板 2
3. **涉及钱、资质、合规、敏感数据吗？** 涉及 → 模板 2
4. **你脑子里已经有明确画面，并且能说清楚吗？** 说不清 → 模板 1；说得清 → 模板 2
5. **是给自己用的小工具 / 一次性脚本吗？** 是 → 模板 1

补充说明：**需求是否说得清**会影响体验，但不应作为主要判据——

- 说得清 + 代价低 → 模板 1（你把要求写全，AI 放手做）
- 说不清 + 代价低 → 模板 1（AI 按"最稳定最好用"补全，你事后看决策记录）
- 说得清 + 代价高 → 模板 2（让 AI 验一遍你的描述有没有漏）
- 说不清 + 代价高 → **必须模板 2**（让 AI 把它从你脑子里问出来）

拿不准就先用**模板 1 开工**，但把模板 2 的「需求澄清维度清单」贴上去，让 AI 拿它自查一遍再动手。

## 混用配方（推荐）

两个模板不是互斥的，最实用的三种组合：

| 配方 | 做法 | 适合 |
| --- | --- | --- |
| **A（纯懒人）** | 直接用模板 1 | 小工具、原型、自己用 |
| **B（纯精细）** | 直接用模板 2 | 正式交付 |
| **B→A 链式** | 先用模板 2 问清楚需求并产出「需求规格确认书」，确认后再用模板 1 的规则让 AI 放手实现 | **最推荐**：需求由你定，实现由 AI 定 |

链式用法的关键动作：把模板 2 产出的「需求规格确认书」作为模板 1 里【第 1 层 · 硬约束】的内容抄进去。

---

## 怎么用这两个模板

任选一种，效果一样：

1. **对话式**：把模板正文整段作为第一条消息发给 AI 编码助手，然后在末尾补充你的项目描述。
2. **项目内固化（推荐）**：把模板另存为项目根目录的 `AGENTS.md`，多数 AI 编码工具（含 Codex）会自动读取，之后每次对话都生效。
3. **工具规则文件**：放进 Cursor / Windsurf / Copilot 等工具的 rules / instructions 文件。
4. **团队规范**：作为团队内部的"需求与交付约定"文档，人工评审也可对照使用。

> 提示：模板 1 末尾有【项目简述】占位小节，填得越具体，AI 自主判断越准；模板 2 不用填，因为它会来问你。

## 两个模板共用的底层原则

无论用哪个模板，这两条都建议保留：

1. **需求 ≠ 实现**。需求是"做什么"，实现是"怎么做"。懒人版只放手实现层，精细版两层都确认。
2. **重大变更必须显式确认**。引入新技术栈、改变架构、花钱、破坏性操作——这四类事情，任何模式下都不应该由 AI 悄悄决定。
